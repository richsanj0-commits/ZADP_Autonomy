ZADP hardware twin: build and setup guide

Three ESP32 robots as haul trucks on a 1 m x 1 m arena (1:200). MATLAB twin leads, robots follow. Every number is quoted from twin3d/params/twin_params.m, firmware/zadp_bot/include/config.h or the docs named in the text.

1. What it is

The ZADP web app plans a dump site. tools/export_plan.py turns the plan into JSON. A MATLAB brain fills the pile spots with three simulated robots, with no collisions and no deadlock. The same route steps are sent over MQTT to three real ESP32 robots. Each robot drives its step with its own encoder controller, which mirrors the twin's controller. An overhead webcam finds ArUco markers and publishes the true pose of each robot. The twin leads and the robots follow. A robot stands for one 20.0 x 16.8 m haul truck. Piles exist only in the twin: on hardware the robot only drives to the spot and back.

2. Components

ItemSpec (from the repo)
Robot x 3ESP32 WROOM-32 devkit; TB6612FNG driver; 2 x N20 geared motors, 300 RPM at the wheel (P.bot.motorNoLoadRpm), with quadrature encoders (2772.2 counts per wheel revolution at 4x, P.bot.encoderCPR); 2S battery; Mini 360 buck set to 5 V into VIN.
MechanicsWheel diameter 34 mm. Track 75.3 mm (wheel centre to centre). Chassis 100 x 84 mm; axle 76 mm from the nose and 24 mm from the back. Maximum wheel speed 0.534 m/s, cruise 0.20 m/s, acceleration 0.5 m/s^2.
Sensing on the robotEncoders only. No IMU, no ToF. Absolute pose comes from the camera (3 mm, 1 deg, P.cam).
ArenaFloor 1.0 x 1.0 m plus a 0.25 m apron below the gate edge (parking and return loop). The floor must extend to the four corner markers: marker centres at x -0.06..1.06, y -0.31..1.06 (a 60 mm marker adds 0.03 m each side).
MarkersRobot ids 1-3, corner ids 10-13, dictionary DICT_4X4_50, 60 mm black square (6x6 modules of 10 mm including border), 10 mm white quiet zone. Printed by the user (section 5).
CameraUSB webcam straight above the arena. The whole arena, apron and four corner markers in view, fixed focus and exposure. Default capture 1280 x 720, 30 Hz (P.cam.rateHz).
PCMATLAB R2026a (base MATLAB for the link, Simulink and Simulink 3D Animation for the model; the Unreal viewer is not used); Python 3 with paho-mqtt, numpy, opencv-contrib-python (and Pillow for the marker sheets); Mosquitto 2.x; PlatformIO for the firmware; WiFi network shared by the PC and the robots.

  • Supply: battery + goes to TB6612 VM and to the buck input. Buck output (5 V) goes to the ESP32 VIN. TB6612 VCC is 3.3 V from the ESP32 3V3 pin. Encoders are powered from 3.3 V.
  • GPIO 34, 35, 36, 39 are input-only and have no internal pull-ups. If the encoder outputs are open collector, add external pull-ups to 3.3 V.
  • One common ground for battery, buck, ESP32, TB6612 and encoders.
  • Direction flags in config.h: MOTOR_L_INVERT 1, MOTOR_R_INVERT 0, ENC_L_DIR 1, ENC_R_DIR -1. They come from the reference micromouse and must be re-checked on each robot with the bench self-test (firmware/README.md section 3).
  • Battery sag resets the ESP32 (brown-out). firmware/README.md section 5 lists a 470-1000 uF capacitor at VM and a thick ground wire.

4. Firmware

PlatformIO project in firmware/zadp_bot, pinned: espressif32 @ 7.0.1 (arduino-esp32 core 2.0.17, ESP-IDF 4.4.7, FreeRTOS), knolleary/PubSubClient @ 2.8, bblanchon/ArduinoJson @ 7.2.1 (built with ARDUINOJSON_USE_DOUBLE=1 for the camera time stamp). The first build fetches the two libraries (internet once). include/motion_core.h is portable C++11 (odometry, wheel PI, control laws, state machine, camera fusion); src/*.cpp are the FreeRTOS tasks below. setup() turns the motors off, starts the encoders (PCNT hardware counters; env bot1_isr = GPIO interrupts), creates the queues and starts five pinned tasks; loop() deletes itself.

Data: ctrlQ (8, FIFO) commands to control; camQ and snapQ (length 1, overwrite) latest camera fix and state snapshot; a task notification sends the acknowledgement telemetry; an event group carries WiFi / MQTT up; a mutex guards the MQTT client. Safety: motors off at boot; MQTT down or comms stuck for 0.3 s stops the motors; any new command ends a bench raw test (capped at 10 s); the task watchdog (1 s, reset) watches only the control task.

  1. copy zadp_bot\include\secrets.example.h zadp_bot\include\secrets.h. Set WIFI_SSID, WIFI_PASS, MQTT_HOST (the PC's LAN address, same as P.mqtt.broker). The file is git-ignored. Without it the build stops.
  2. Robot number = environment. bot1, bot2, bot3 set BOT_ID, hence topics zadp/botN/cmd and zadp/botN/telemetry, client id zadp-botN and the start pose on slot PN. PCB boards: bot1_pcb..bot3_pcb.
  3. In firmware/zadp_bot: pio run -e bot1 -t upload, then pio device monitor -e bot1 (115200 baud). Repeat for 2 and 3. Label each robot.

Where to change a number

Edit twin3d/params/twin_params.m. In MATLAB, link_write_config(twin_params()) writes twin3d/link/link_config.json, which bridge.py, fake_bot.py and aruco_node.py read. Then python twin3d/link/py/check_numbers.py compares config.h with it (43 rows, all must read ok); MATLAB test_firmware runs the same check. Entries tagged CALIBRATE in config.h (TRACK_SCALE, PWM_DEADBAND, PWM_PER_MPS) are per robot. TRACK_SCALE must equal P.bot.trackScale (default 1.0; the reference micromouse needed 1.14). The per-wheel counts per revolution (2772.1 left, 2772.3 right) average to the twin's 2772.2.

5. Arena, camera and markers

Layout

  • Site polygon (site metres 10..190): (0.05, 0.05), (0.95, 0.05), (0.95, 0.75), (0.75, 0.95), (0.05, 0.95). Gate on the bottom edge at x 0.5.
  • Spine 0.24 m wide. IN lane x 0.44 (up), OUT lane x 0.56 (down), both 0.12 m wide.
  • Two zones, one each side of the spine.
  • Apron y -0.25..0. One-way loop: queue row heading west, P1 under the IN lane, IN lane, site, OUT lane, return row y -0.0555 east, east column down, P3, P2, P1.
  • Parking P.brain.parking, heading west (pi), y -0.159: P1 x 0.44 (head), P2 x 0.75, P3 x 0.90 (tail). Robot N starts on slot PN. After that a returning robot always parks at P3 and moves up (rolling queue).

Markers (P.cam)

  • Corner ids 10, 11, 12, 13 at (-0.06, -0.31), (1.06, -0.31), (1.06, 1.06), (-0.06, 1.06). Orientation free; only centres are used.
  • Robot id = robot number. Marker centred on the robot top, 0.026 m ahead of the axle (markerOffset), printed arrow toward the nose.
  • Plane height: markerHeight = cornerHeight = 0.050 m. Measure the robot top and set both. Corner markers sit on blocks of that height, so the corner plane is the robot marker plane and there is no parallax. If the corners lie on the floor, set cornerHeight 0 and cameraHeight (default 1.20 m); parallax is then corrected about the image-centre nadir.
  • Capture delay assumed 0.030 s (captureDelay).

Camera pose. aruco_node.py fits a homography from the image to the arena plane using the four corner marker centres (kept from the last frame that showed all four, so a robot hiding a corner does not lose it). It maps each robot marker's four corners to the arena, takes the centre and the heading (bottom-edge middle to top-edge middle), and subtracts markerOffset along the heading to get the axle centre. It publishes {bot, x, y, heading, t, age} on zadp/cam/pose. Optional lens calibration: --calib file.json (camera_matrix, dist_coeffs); there is no undistortion otherwise, and the apron outside the corner markers is extrapolated.

Marker sheets. twin3d/link/markers/make_markers.py writes robots_A4.pdf, corners_A4.pdf, marker_<id>.png and placement.txt from link_config.json (needs opencv-contrib-python and Pillow). Print at 100 % and check the 50 mm bar. The repo ships the script only, no sheets.

6. MQTT contract summary

Broker P.mqtt.broker:1883, JSON UTF-8, SI units, arena frame. N = 1..3. Full text, field semantics and the 18 decisions: twin3d/link/TOPICS.md.

TopicDirectionRateQoSPayload
zadp/botN/cmdbrain to robotnew command, then bridge repeats at 10 Hz1 new seq, 0 repeats{id, truck, seq, action, x, y, heading, speed[, dir, tol]}
zadp/botN/telemetryrobot to brain20 Hz, plus at once on a new seq0, not retained{id, seq, encL, encR, x, y, heading, state}
zadp/cam/posecamera to all30 Hz per visible robot0{bot, x, y, heading, t, age}
  • action: goto (follow the leg line to x, y, no final turn), turn (in place, dir +1 CCW, -1 CW, 0 shortest; tol in degrees, default 3, 1 at dump stops), dump (4 s in place), stop. speed default and cap 0.20 m/s.
  • seq is uint32 and opaque. Same seq = repeat (refreshes the watchdog only). Any other seq replaces the command at once.
  • Robots subscribe to cmd at QoS 1 and cam/pose at QoS 0, clean session. Client id zadp-botN.
  • state: idle, moving, turning, dumping, arrived (the command with this seq is done and both wheels are below 2 mm/s), offline (last will only). The brain waits for arrived with its seq.
  • cam/pose gives the axle pose. t drops duplicates and out-of-order messages. age = publish time - t on the camera PC, so no clock sync is needed.

Stop latency: MATLAB closed or crashed, robots idle after 0.3 s. MATLAB hung, 1.3 s (1.0 + 0.3). Bridge or broker gone, 0.3 s. The brain ends the run if a robot reports offline or its telemetry stops for 2 s.

7. Launch order

Everything runs on the PC that runs MATLAB unless stated. Source: twin3d/HANDOVER.md section 14.

  1. Broker. Install Mosquitto 2.x. Create C:\mosquitto\zadp.conf: 
    listener 1883 0.0.0.0
allow_anonymous true
    Closed test network only. Allow inbound TCP 1883 in the Windows firewall. Stop the installed service (net stop mosquitto, admin shell), then: 
    "C:\Program Files\mosquitto\mosquitto.exe" -v -c C:\mosquitto\zadp.conf
    Set P.mqtt.broker in twin_params.m to the PC's LAN address ('localhost' if MATLAB and the broker share the PC).
  2. Python. 
    pip install paho-mqtt numpy opencv-contrib-python pillow
  3. Flash each robot (section 4), then run the bench self-test and a single-robot MQTT test from firmware/README.md sections 3-4. Watch with mosquitto_sub -h <ip> -t "zadp/#" -v.
  4. Markers. In MATLAB link_write_config(twin_params()), then 
    python twin3d\link\markers\make_markers.py
    Print robots_A4.pdf and corners_A4.pdf at 100 %. Fit robot marker N on robot N (arrow to the nose). Place corners 10-13 per placement.txt, on blocks so their plane equals the robot marker plane. Set P.cam.markerHeight = P.cam.cornerHeight to the measured height.
  5. Camera check, alone: 
    python twin3d\link\py\aruco_node.py --camera 0 --broker <ip> --show
    It prints homography ready (4 corner markers), then poses. Extra arguments for run_real go in camArgs, for example --camera 1 --width 1920 --height 1080.
  6. Place the robots on P1, P2, P3 (x 0.44 / 0.75 / 0.90, y -0.159, heading west) and power them. run_real requires each robot within 30 mm and 15 deg of its slot.
  7. No-hardware test first. Same code path with the loopback bridge, fake_bot.py robots and a simulated camera: 
    run('E:\catrover_dumpautonomy\twin3d\startup.m')
R = run_real('dry');
  8. Real run. 
    run('E:\catrover_dumpautonomy\twin3d\startup.m')
R = run_real('real', struct('maxTime', 60));   % first run
R = run_real();                                % default maxTime 600
    run_real writes link_config.json, checks Python, numpy, paho-mqtt, OpenCV and the broker, starts bridge.py (broker mode, no fallback) and aruco_node.py, waits up to 20 s for the four corners and 15 s for telemetry and a pose from robots 1-3, checks the slots, then runs brain_run_linked with syncToReal and a live 3D view drawn at the camera poses. An error, Ctrl+C or closing the view sends stop to all robots (twice) and kills the helper processes. Raise maxTime step by step. A full fill takes about 2880 s of sim time, the same in wall time. R.lk holds twin-vs-real error, latency and hold times per robot.

8. How the simulation was planned around the hardware

Scale and numbers

The robot sets the scale. 0.100 x 0.084 m is one 20.0 x 16.8 m truck, so 1 arena m = 200 site m (P.scale.sitePerArena). The arena is 200 x 200 m, about 10 acres. Physics uses the real robot numbers in P.bot (wheel, track, counts, motor lag 0.08 s, 1 % per-wheel slip). P.truck (65 mm high, bed tilt 50 deg, 4 s dump) is visual only: a generic haul truck drawn over the robot, no brand marks.

Parking and trucks

Three robots stand for an endless stream of trucks. Every entry from parking is a new truck (W.truckNo counts them). The rolling queue P3 to P2 to P1 is the parking. A fixed bay per robot would need a wider apron and breaks the all-or-nothing section grants. Each truck carries the plan payload times a load factor drawn uniformly from 0.85..1.00.

Lane sections and safety

  • The drivable area is cut into sections (zones Z1, Z2, IN_LOW, OUT_LOW, J, UP, apron sections). A robot starts a move only while it holds every section its swept body (plus 8 mm) touches. Long drives are cut into 5 cm pieces and a section is released only after the last piece that needs it.
  • The whole inbound route and the zone lock are granted at once before a truck leaves the queue head. The whole exit route is granted before it leaves the dump stop. Waiting happens only in apron slots or at the dump stop.
  • Deadlock watch: a wait cycle of 10 s, or nobody moving or dumping for 60 s before the run has ended, ends the run and is reported.
  • Monitors, all zero in every verified run: robot-robot overlaps, robot-pile hits, off-site, section ownership, deadlocks.
  • Fill order: lowest plan order reachable in a zone; branch spots after their zone; lane spots last, one truck at a time, deepest first.

Pile maths

Same as calc(t) in the planner: V = payload / rho, r = cbrt(3V / (pi tan(repose))), h = r tan(repose), with rho 1.8 t/m^3 and repose 37 deg. Computed at site scale, drawn at 1:200. 500 t gives V 277.8 m^3, site r 7.06 m, h 5.32 m; arena r 35.3 mm, h 26.6 mm. The real radius is capped at the planned one, so planned clearances hold. During a dump the pile grows with frac^(1/3).

What a run shows on screen

A 3D view in base MATLAB graphics (about 8 frames/s at 1280 x 720, software rendering): dirt ground, apron slab with parking slots P1-P3, the site on a raised pad with a berm open at the gate, zones, the spine with IN (blue) and OUT (red) centre lines, three yellow haul trucks whose bed tips to 50 deg while dumping, and cone piles that grow during each dump. Views: top, orbit, gate, follow robot N. The HUD shows sim time, site time, trucks sent, piles placed out of spots, coverage percent and collisions. In run_real the trucks are drawn at the camera poses, so the view shows the real robots.

9. Status

Tested in simulation and loopback

  • Brain and twin: full fills 125 / 125 / 125 of 125 piles for seeds 1-3; all monitors 0; four more maps in maps_results.md and four in twin3d/maps; run_all_tests passed on the last full run.
  • Link, loopback with fake_bot.py: 120 s demo, 115 of 115 commands acknowledged, twin-vs-real position error mean 5.2 mm and worst 24.8 mm, command round trip mean 12.9 ms, twin violations 0.
  • run_real('dry') (loopback bridge, fake robots, simulated camera through the real geometry code), covered by test_run_real.
  • Firmware logic through a line-by-line JavaScript mirror of motion_core.h: 47 passed, 0 failed (goto 40 of 40 arrived, turns within tolerance, watchdog, fusion, odometry in float32). config.h against twin_params.m by check_numbers.py (43 ok). All 9 src/*.cpp syntax-checked with the xtensa g++ 8.4 against arduino-esp32 2.0.17 headers (104 variant compiles, 0 errors, 0 warnings), with stand-ins for the two libraries.
  • Camera geometry on synthetic pixels (test_aruco_geometry.py).

First verified on your bench

  • Nothing has run on an ESP32: motor and encoder directions, counts per revolution, dead band, PI gains, the PCNT encoder counters (20-turn wrap check), 200 Hz timing under WiFi load, task stack margins (w), the task-watchdog reset path, brown-out behaviour. The PlatformIO build with the two libraries has not been done. The arduino-esp32 core 3.x LEDC branch was not compiled. The C++ host test was not run (no host compiler); the JS mirror ran.
  • No real broker has been connected: the MQTT path of the firmware, bridge.py broker mode and aruco_node.py is untested against Mosquitto.
  • aruco_node.py has never run on a camera. No OpenCV on the development PC, so the marker sheets have not been generated. Run python twin3d\link\markers\make_markers.py yourself (section 7, step 4). Expect to tune the camera node (no undistortion, extrapolated apron).
  • Calibration: TRACK_SCALE (copy to P.bot.trackScale), PWM_DEADBAND, PWM_PER_MPS, per-wheel CPR; measured robot top height for P.cam.markerHeight and cornerHeight.
  • Known limits that stay: the apron is cramped (margins of 4 to 10 mm over the tracking error, so stops must be centred on their end point and drives must follow the leg line); lane spots are filled last and one truck at a time.
